### [CNCF] GPU autoscaling on Kubernetes with KEDA: Building an external scaler

- **発表日**: 2026-05-27 (水 11:00 UTC / 20:00 JST)
- **カテゴリ**: 機能 (Feature / Kubernetes Autoscaling)
- **影響範囲**: Kubernetes 上で GPU ワークロード (vLLM、Triton、学習ジョブ、エージェント推論スタック) を運用し、KEDA (Kubernetes Event-Driven Autoscaler) ベースのオートスケーリングを検討するプラットフォーム・SRE チーム。KEDA core (graduated CNCF project)、NVIDIA GPU ノード環境
- **核心要約** (本文ベース):
  - **何 (What)**: 標準の KEDA スケーラーが CPU・メモリのみを参照し、GPU シグナル (utilization・memory・temperature・power draw) を考慮できない問題を解決するため、GPU ノードごとに DaemonSet 形式で動作する **カスタム External Scaler (keda-gpu-scaler)** を実装した事例の共有
  - **どのように (How)**: (1) **CGO 制約の回避** — KEDA core は `CGO_ENABLED=0` でビルドされる一方、NVIDIA Management Library (NVML) は CGO を必要とするため、GPU スケーラーを KEDA core に直接追加することはできません。(2) **per-node DaemonSet パターン** — NVML 呼び出しは同一ノードの GPU に限定されるため、device plugins / metrics server と同様の per-node エージェントパターンを採用。(3) **gRPC 公開** — 各 Pod が `go-nvml` でローカル GPU メトリクスを収集し、KEDA の ExternalScaler インターフェースで gRPC として公開、KEDA operator が接続して HPA 判定を実行。(4) **公開メトリクス** — `gpu_utilization` (SM 使用率)、`memory_utilization`、`memory_used_percent` (VRAM 使用率)、`temperature` (°C)、`power_draw` (W)。マルチ GPU ノードは `max/min/avg/sum` 集計、または特定 GPU インデックス指定が可能。(5) **プリビルトプロファイル** — `vllm-inference` (memory_used_percent target 80% / activation 5%、scale-to-zero 対応)、`triton-inference` (gpu_utilization 75% / 10%)、`training` (gpu_utilization 90% / 0%、scale-to-zero なし)、`batch` (memory_used_percent 70% / 1%)。Helm インストール: `helm install gpu-scaler deploy/helm/keda-gpu-scaler --namespace gpu-scaler --create-namespace`。(6) **GPU 不要のテスト** — mock collector と 11 件の e2e テストが、疑似 GPU データで IsActive → GetMetricSpec → GetMetrics フローを CI 上で検証
  - **なぜ・効果 (Why / Impact)**: 標準 KEDA の CPU/メモリベーススケーリングはアクセラレーター利用率のミスマッチを生み、GPU リソース浪費・推論レイテンシ増大・電力消費増の原因になります。GPU シグナルベースのスケーリングはコスト問題だけでなく、Scope 3 排出削減 (GreenOps) の観点でも意味を持ちます。KEDA の ExternalScaler インターフェースが graduated CNCF プロジェクトの拡張性を示す事例
  - **主要データ**: 5つの GPU メトリクス (utilization, memory_utilization, memory_used_percent, temperature, power_draw) / 4つのプリビルトプロファイル / 11件の e2e テスト / target・activation 閾値 (vllm 80%/5%、triton 75%/10%、training 90%/0%、batch 70%/1%)
- **原文リンク**: https://www.cncf.io/blog/2026/05/27/gpu-autoscaling-on-kubernetes-with-keda-building-an-external-scaler/

### [Cisco Blogs] A new model for infrastructure security: How Cisco defends against AI threats

- **発表日**: 2026-05-27 (水 18:33 UTC / 2026-05-28 03:33 JST)
- **カテゴリ**: セキュリティ (Security / Defensive Architecture)
- **影響範囲**: AI 時代のセキュリティ運用モデルを再設計中の大規模エンタープライズの CISO・SOC・セキュリティ運用チーム。Cisco 自社ネットワーク (数百万デバイス・数千アプリケーション・増加中の AI エージェント) 規模の環境
- **核心要約** (本文ベース):
  - **何 (What)**: Cisco が自社のセキュリティ運用モデルを「脆弱性開示 → パッチ開発 → 変更ウィンドウ → 手動承認 → 展開」という週単位サイクルから、4つの柱 (Real-time visibility、Continuous exposure validation、Runtime protection、Modernization) に再構成した運用モデルを公開
  - **どのように (How)**: (1) **Real-time visibility first** — すべての資産・アイデンティティ・サービスアカウント・クラウド権限・API を継続更新するインベントリ。オーナーシップ・重要度・侵害時の影響まで含めます。(2) **Continuous exposure validation** — CVSS ベースの周期的レビューに代えて、マシン速度で実際の攻撃シミュレーションを実行し、理論的リスクではなく実際に exploit 可能な項目を優先修正。attack path 解析。(3) **Runtime protection as a bridge** — 根本修正までの時間を稼ぐ一時的保護。Hypershield クラスのセグメンテーション (Container Orchestration)、Live Protect、eBPF ベースの Tetragon エージェント (再起動・バイナリ変更なしでリアルタイムに脆弱性遮断)。(4) **Modernization** — EOL システム廃止、安全でないレガシーサービスの除去、迅速なパッチ適用に向けたインフラ近代化。(5) **Outside-in 優先順位** — インターネット露出エッジから優先的にパッチ速度を加速し、コア方向へ段階的に進めます。最大のセキュリティゾーンを区切る境界ファイアウォール優先。(6) **Anthropic Project Glasswing / OpenAI Daybreak** など frontier モデルとの協業を基盤として運用モデルを構築
  - **なぜ・効果 (Why / Impact)**: AI 駆動型攻撃ツールにより、「公開 〜 武器化」までの時間が週単位から時間/分単位へ圧縮されています。従来の閾値ベースのリスク管理では、攻撃者が閾値以下の脆弱性まで武器化できるため、もはや有効ではないという診断です。本文引用:「これまで気にしなかったものこそ、今最も気にすべきもの。基準線が下がった」
  - **主要データ**: 本文内に定量数値の明示なし (自社ネットワーク規模 — 数百万デバイス・数千アプリケーション水準)。言及された標準・ツール: CVSS (Common Vulnerability Scoring System)、Hypershield、Live Protect、eBPF Tetragon。パートナーシップ: Anthropic Project Glasswing、OpenAI Daybreak
- **原文リンク**: https://blogs.cisco.com/cisco-on-cisco/how-cisco-defends-against-ai-threats

- **影響範囲**: Frontier LLM を導入・評価する企業の AI セキュリティ・ガバナンスチーム、モデルカード/安全性レポートを procurement 意思決定の根拠として使用する組織。評価対象 15モデル運用環境
- **核心要約** (本文ベース):
  - **何 (What)**: Cisco の closed/proprietary frontier モデル 15件 に対する **multi-turn 攻撃評価レポート** を公開 — single-turn の攻撃成功率 (ASR: Attack Success Rate) は multi-turn ASR の信頼できる代理指標とはならないという結論
  - **どのように (How)**: (1) 固定スナップショットコーパス — single-turn 30,090 プロンプト (モデルあたり 2,006) + multi-turn 1,456 会話 6,986 攻撃。(2) Cisco Integrated AI Security and Safety Framework taxonomy を適用。(3) 評価対象 — OpenAI (GPT-5.2、GPT-5.4 ファミリ)、Anthropic (Claude Opus 4.5・4.6、Sonnet 4.5・4.6、Haiku 4.5)、Google (Gemini 3 Pro)、Amazon (Nova Lite、Nova Micro、Nova 2 Lite)、xAI (Grok 4.1 Fast — reasoning/NR 両構成)。(4) 評価結果 — multi-turn ASR レンジ **7.89% 〜 88.30%**、single-turn ASR レンジ **2.19% 〜 64.91%**。両方式は同じモデル順位・失敗マップ・tail risk 分布を生成しません
  - **なぜ・効果 (Why / Impact)**: 実際の攻撃者は reframe・decompose・persona・gradual escalation により multi-turn で動的に行動します。single-turn ベンチマークに基づくモデルカードと procurement 意思決定の間に構造的なギャップが存在するという主張です。本文の引用結果: GPT-5.4 は 2.74% → 24.68% (9×)、Gemini 3 Pro は 18.10% → 73.35% (4×)、Grok 4.1 Fast NR は 88.30% (最高)。Claude ファミリは single-turn 2.19〜3.64% → multi-turn 11.16〜16.20% (最も狭いギャップ)。Anthropic のように「safety を強調する」ラボほど multi-turn ギャップが狭い傾向の相関を観察
  - **主要データ**: 評価モデル数 15 / single-turn 30,090 プロンプト (モデルあたり 2,006) / multi-turn 1,456 会話 6,986 攻撃 / multi-turn ASR 7.89〜88.30% / single-turn ASR 2.19〜64.91% / 最低: Nova 2 Lite 7.89% / 最高: Grok 4.1 Fast NR 88.30% / 先行研究引用: open-weight 8モデル (Death by a Thousand Prompts) の multi-turn 2× 〜 10×、5ターン後の脆弱性 +71%
