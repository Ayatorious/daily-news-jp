### [Kubernetes Blog] Reconciling the Past: Correcting Records for Unfixed Kubernetes CVEs

- **発表日**: 2026-05-26 (火 09:30 PST / 2026-05-27 02:30 JST)
- **カテゴリ**: セキュリティ (Security)
- **影響範囲**: すべての Kubernetes クラスター管理者およびセキュリティ運用チーム。影響を受ける CVE は 3 件 (CVE-2020-8561、CVE-2020-8562、CVE-2021-25740)。CVE レコード修正適用日: 2026-06-01
- **核心要約** (本文ベース):
  - **何 (What)**: Kubernetes Security Response Committee (SRC) が 2026 年 6 月 1 日に未修正 (unfixed) の CVE 3 件のレコードを訂正します。既存 CVE レコードに誤って記載されていた「fixed version」フィールドを削除し、正しく未修正状態として表示します
  - **どのように (How)**: (1) **CVE-2020-8561 (Medium 4.1)** — kube-apiserver が admission webhook 通信時に HTTP redirect を追跡する動作を悪用した内部ネットワーク SSRF が可能。AdmissionWebhookConfiguration を設定できる行為者が API サーバーのリクエストを内部プライベートネットワークへ誘導可能。未修正の理由: 標準 HTTP クライアント挙動の変更が正常な連携を破壊するため。緩和策: API サーバーのログレベルを 10 未満に設定 + `--profiling=false`。(2) **CVE-2020-8562 (Low 3.1)** — API サーバー プロキシの DNS TOCTOU (Time-of-Check to Time-of-Use) 競合状態により IP 制限を回避可能。検証用 DNS 解決と実接続用 DNS 解決が個別に行われる点を攻撃者が操作。緩和策: dnsmasq などのキャッシュリゾルバの導入 + `min-cache-ttl` の設定。(3) **CVE-2021-25740 (Low 3.1)** — Endpoints / EndpointSlice API オブジェクトに任意 IP を指定可能で、LoadBalancer / Ingress のトラフィックを他ネームスペースへ転送可能。緩和策: `kubectl auth reconcile` により Endpoints の書き込み権限を広範な role から除去 (Hardened RBAC)
  - **なぜ・効果 (Why / Impact)**: OSV (Open Source Vulnerabilities) ファイル生成作業中に CVE レコードの精度不足が判明。訂正適用後は vulnerability スキャナが従来 false negative で見落としていた環境でも該当の脆弱性を検出するため、6 月 1 日以降のスキャナ結果の変化に備える必要があります
  - **主要データ**: CVE 3 件 (CVE-2020-8561 CVSS 4.1、CVE-2020-8562 CVSS 3.1、CVE-2021-25740 CVSS 3.1) / レコード訂正日 2026-06-01 / 識別・貢献者 QiQi Xu、Javier Provecho、Rory McCune
- **原文リンク**: https://kubernetes.io/blog/2026/05/26/reconciling-unfixed-kubernetes-cves/

### [CNCF] How Jaeger is evolving to trace AI agents with OpenTelemetry

- **発表日**: 2026-05-26 (火 11:00 UTC / 20:00 JST)
- **カテゴリ**: 機能 (Feature)
- **影響範囲**: Jaeger を利用する observability 運用チーム、および AI エージェント / LLM アプリケーションを運用・監視する SRE・プラットフォームチーム。Jaeger v2 ユーザー
- **核心要約** (本文ベース):
  - **何 (What)**: 分散トレーシング (Distributed Tracing) ツールである Jaeger が、マイクロサービス環境を超え、生成 AI アプリケーションと自律エージェント (autonomous agent) の実行パス (プロンプト組み立て、ベクター DB 検索、外部ツール呼び出し等) のトレースまでサポートするよう進化中
  - **どのように (How)**: 2 段階アプローチ。(1) **Jaeger v2** — コアアーキテクチャを再構築し、OpenTelemetry をネイティブ統合。中間変換ステップを排除して ingestion 性能を向上。(2) **3 つのオープン標準を採用** — Model Context Protocol (MCP)、Agent Client Protocol (ACP)、Agent–User Interaction Protocol (AG-UI)。MCP は AI モデルが外部データソースに安全にアクセスするための標準、ACP は UI と AI エージェント・サイドカー間通信の標準。バックエンドは自然言語クエリ (例: 決済サービスで latency が 2 秒を超える 500 系エラー) を決定論的 (deterministic) な trace クエリへ変換。運用側はクラウド LLM、またはデータプライバシー要件が厳しい場合はローカル SLM を選択可能。UI は legacy Redux から Zustand + React Query へ移行 (Jaeger UI issue #3313)、assistant-ui + AG-UI ベースのインアプリアシスタントを導入
  - **なぜ・効果 (Why / Impact)**: AI の役割を protocol 変換・クエリ生成に限定することで、open-ended なチャットボットに伴うハルシネーション (hallucination) リスクを最小化。エンジニアと AI エージェントが協調してデバッグできる環境を提供
  - **主要データ**: 本文内に定量数値の明記なし。貢献チャネル: CNCF LFX Mentorship、Google Summer of Code (GSoC)
- **原文リンク**: https://www.cncf.io/blog/2026/05/26/how-jaeger-is-evolving-to-trace-ai-agents-with-opentelemetry/

### [Cisco Blogs] Securing campus and branch networks from boot to transport with full-stack PQC

- **発表日**: 2026-05-26 (火 15:00 UTC / 2026-05-27 00:00 JST)
- **カテゴリ**: 機能 (Feature / Security Architecture)
- **影響範囲**: Cisco ネットワークスイッチ (キャンパス・ブランチ環境) を運用する組織、および CNSA 2.0 など耐量子暗号関連の規制・標準への対応を進めるインフラ・セキュリティ責任者
- **核心要約** (本文ベース):
  - **何 (What)**: Cisco が Cisco Live Amsterdam 2026 で発表した **full-stack post-quantum cryptography (PQC)** アーキテクチャ。ハードウェアの secure boot からデータ転送まで、ネットワークスタック全層に耐量子アルゴリズムを適用
  - **どのように (How)**: NIST 承認の PQC アルゴリズムを secure boot プロセスからデータ転送プロトコルまで統合。Trust Anchor module (TAm) → microloader → bootloader → OS の順に検証されるハードウェアルート信頼チェーンに PQC を組み込み、署名偽造・将来の復号攻撃に備えます。Silicon からアプリケーション層まで全体にわたり cryptographic agility を提供
  - **なぜ・効果 (Why / Impact)**: 「harvest now, decrypt later」 (現時点で暗号文を収集し、量子コンピュータ登場後に復号する) 脅威への対応。RSA・Diffie-Hellman・ECC ベースの既存暗号が量子攻撃に脆弱になることを見据え、量子時代到来前に標準ベースの保護体系を先行構築
  - **主要データ**: 本文内に定量数値の明記なし。言及された標準: NIST PQC、CNSA 2.0。発表イベント: Cisco Live Amsterdam 2026。追加のプラットフォーム改善は 2026 年以降も継続予定
- **原文リンク**: https://blogs.cisco.com/networking/securing-campus-and-branch-networks-from-boot-to-transport-with-full-stack-pqc

### [Cisco Blogs] Why Network Segmentation Projects Fail: Four Patterns

- **発表日**: 2026-05-26 (火 12:00 UTC / 21:00 JST)
- **カテゴリ**: その他 (Research Report)
- **影響範囲**: ネットワークセグメンテーション (macro / micro-segmentation) プロジェクトを計画・運営中のセキュリティ・ネットワークチーム。調査対象は従業員 500 名以上の米国組織
- **核心要約** (本文ベース):
  - **何 (What)**: Cisco 2026 Segmentation Report が新たに公開。失敗に終わったセグメンテーションプロジェクト 400 件を 12 個の要因 (一般 IT PM 課題 + セグメンテーション固有課題) で分析し、4 つの失敗パターンを抽出
  - **どのように (How)**: 4 つの失敗パターンの定量分布 — (1) **Perfect Storm 50%**: ほぼすべての面で同時に失敗。IT PM 課題とセグメンテーション技術課題が同時発生。(2) **Diffuse Friction 33%**: 単一面で大きな失敗はないが、複数次元に蓄積した中程度の摩擦で進捗停滞。(3) **Operational Drag 9%**: 目標・スポンサーシップは良好だが、セグメンテーションポリシーの作成・維持負担が持続不可能。(4) **Scope & Visibility Trap 8%**: 範囲拡大・非現実的スケジュール・複雑な環境への可視性不足で失敗
  - **なぜ・効果 (Why / Impact)**: 失敗プロジェクトの **80% 以上がセグメンテーション固有の要因で頓挫** — 可視性ギャップ、ポリシー維持負担、ツール制約などは一般的なプロジェクト管理強化だけでは解決不可。セグメンテーション固有の対策 (asset inventory、ポリシー自動化、可視性ツール) の必要性を強調
  - **主要データ**: 分析対象 400 件の失敗プロジェクト / 米国・従業員 500 名以上の組織 / 評価要因 12 個 / 4 つの失敗パターン比率 50・33・9・8% / 80% 以上がセグメンテーション固有要因
- **原文リンク**: https://blogs.cisco.com/security/why-network-segmentation-projects-fail-four-patterns
