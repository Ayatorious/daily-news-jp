## 🟢 Priority 3 — Announcement / Update / Feature

### [CNCF] What kubectl debug doesn't tell you: The silent evidence gap

- **発表日**: 2026-05-18 (Mon 20:00 JST)
- **カテゴリ**: 機能 / その他 (Feature / Other — Blog)
- **影響範囲**: Kubernetes v1.32 API 仕様における `EphemeralContainerStatus` 型を利用するすべての `kubectl debug` セッション (インシデント対応・SRE ワークフロー・監査トレーサビリティに影響)
- **核心要約** (本文ベース):
  - **何 (What)**: `kubectl debug` で生成された ephemeral container (エフェメラルコンテナ) のセッション終了後、Kubernetes API がそのセッションの終了コンテキスト (exit code・セッション時間・target container 名) を保持しないという「silent evidence gap (沈黙する証拠の欠落)」の問題。
  - **どのように (How)**: Kubernetes v1.32 の `EphemeralContainerStatus` 型には `lastState`・`restartCount` フィールドが意図的に存在しません。通常の `ContainerStatus` は `lastState` で直前の終了情報を保持しますが、ephemeral container は再起動されないという設計前提のもとで両フィールドが除外されています。Pod の state が次回更新で遷移すると `state.terminated` ブロックが消失し、`kubectl get pod ... -o jsonpath='{.status.ephemeralContainerStatuses[*]}'` でも `kubectl logs <pod> -c <debugger>` でも参照不可となります (`container not found`)。`--target` フラグも kubectl CLI 側の機能にとどまり、API フィールドとしては保存されません。
  - **なぜ・効果 (Why / Impact)**: インシデントのハンドオフ時に、一次対応エンジニアが残した exit code 規約 (例: `exit 42` = "connection pool exhausted") がメモから欠落すると API 側で再確認できず、次の担当者が一からの再調査を強いられます。本文ではこの欠落を規制環境 (コンプライアンス監査) における問題としても指摘し、SIG Node あるいは SIG Instrumentation が自然な提案オーナーであると述べています。
  - **主要データ**: 再現シナリオ — `kubectl run debug-target --image=nginx:alpine` → `kubectl debug ... --image=busybox:1.36 --target=nginx -it -- sh -c "echo '...'; sleep 10; exit 42"` → セッション終了直後に `ephemeralContainerStatuses` を参照し、その後 pod 状態が変化すると情報が消失。デモコード: `github.com/opscart/k8s-causal-memory/scenarios/05-ephemeral-exit/`
- **原文リンク**: https://www.cncf.io/blog/2026/05/18/what-kubectl-debug-doesnt-tell-you-the-silent-evidence-gap/
