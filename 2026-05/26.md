### [CNCF] Why Kubernetes policy enforcement happens too late—and what to do about it

- **発表日**: 2026-05-25 (月 11:00 UTC)
- **カテゴリ**: 機能 (Feature)
- **影響範囲**: Kubernetes 環境で Policy-as-Code ツール (OPA、Kyverno、Conftest など) を運用するプラットフォーム / DevOps チーム。特定バージョンへの影響はありません
- **核心要約** (本文ベース):
  - **何 (What)**: Kubernetes 環境におけるポリシー施行 (Policy Enforcement) のタイミング問題 — 信頼性・セキュリティインシデントの多くはアプリケーションコードではなく、設定ミスのあるインフラ (欠落した resource limits、過度に許可された security context、誤った RBAC バインディング) に起因することを指摘
  - **どのように (How)**: 既存の Policy-as-Code ツールが動作する 2 つの時点 (CI/CD パイプラインでの manifest スキャン、admission controller によるクラスタ境界での enforcement) に加えて、**レビュー時点 (review-time) の enforcement** を提案。Pull Request 内の YAML manifest をブラウザでクライアントサイド評価し、CI/CD 統合やクラスタアクセスなしで PR インラインアノテーション (inline annotation) としてポリシー違反を表示。本文で言及されている関連オープンソースプロジェクト: Open Policy Agent (OPA)、Kyverno、GuardOn
  - **なぜ・効果 (Why / Impact)**: 開発者がコード作成・PR レビューを終えた後に CI のポリシー違反でコンテキストスイッチし直すサイクルを短縮。ポリシー品質の問題ではなく「タイミングの問題」という観点を提示
  - **主要データ**: 本文に定量的な数値の明示なし (本文情報が不足)
- **原文リンク**: https://www.cncf.io/blog/2026/05/25/why-kubernetes-policy-enforcement-happens-too-late-and-what-to-do-about-it/

### [CNCF] Zero-Downtime migration from ingress NGINX to Envoy Gateway

- **発表日**: 2026-05-25 (月 11:00 UTC)
- **カテゴリ**: その他 (Migration Case Study)
- **影響範囲**: AWS 環境で Ingress NGINX を運用しており、Gateway API への移行を検討しているチーム。マルチネームスペース運用クラスタでは hostname 設計の考慮が必要
- **核心要約** (本文ベース):
  - **何 (What)**: Ingress NGINX から Envoy Gateway への無停止 (zero-downtime) 移行の事例研究 — AWS Network Load Balancer 環境
  - **どのように (How)**: (1) `ing-switch` ツールで既存 Ingress リソースをスキャンし annotation マッピング・impact rating を生成。(2) **Kind (Kubernetes IN Docker)** でローカル検証環境を構築。(3) Envoy Gateway + AWS NLB の組み合わせに ExternalDNS (自動 DNS レコード管理) と cert-manager (TLS) を結合。(4) 最初の試行は A レコードの直接置換で、DNS TTL が満了するまでトラフィック損失が発生し失敗。(5) 最終的に **AWS Route 53 の weighted DNS record** と ExternalDNS で Ingress と HTTPRoute を同一ホスト名に重み付けして並行運用し、無停止 cutover を達成
  - **なぜ・効果 (Why / Impact)**: 単純な A レコードの swap では DNS TTL が満了するまでクライアントが旧アドレスに resolve し続け、トラフィックドロップが発生。weighted DNS によって transition window の間も安定した到達先を維持
  - **主要データ**: Envoy Gateway は CNCF プロジェクトで graduation 基準を満たす。Envoy Gateway 自体の contributor は 4 名で、1 組織が 51% 以上を貢献。Gateway API 1.5 より前のバージョンでは hostname を Gateway レベルと HTTPRoute レベルの両方で定義する必要あり (マルチネームスペース環境では制約となる)
- **原文リンク**: https://www.cncf.io/blog/2026/05/25/zero-downtime-migration-from-ingress-nginx-to-envoy-gateway/
