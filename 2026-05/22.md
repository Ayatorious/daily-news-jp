### [Cisco] Enhancing Cisco Secure Email Gateway: Safer Clicks and Cleaner Files

- **発表日**: 2026-05-21 (Thu 23:30 JST) — 原文公開 2026-05-21 14:30 UTC
- **カテゴリ**: 機能 (Feature — セキュリティ / Email Security)

- **核心要約** (本文ベース、原文 fetch `selector` 抽出 4,308文字 — retries 0):
  - **何 (What)**: Cisco Secure Email Gateway に **Remote Browser Isolation (RBI)** と **Content Disarm and Reconstruction (CDR)** の2つの新機能をアドオンライセンスとして追加。セキュリティ姿勢を「検知・対応 (detect and react)」から「隔離・無害化 (isolate and neutralize)」へ転換するのが要旨です。
  - **どのように (How)**: ① **RBI** — ユーザーがメール内のリンクをクリックすると該当ページをリモート隔離ブラウザセッションでレンダリングし、脅威をユーザー端末から切り離します。配信時点では良性に見え、数時間後に悪性化する (delayed weaponization) リンクに対応します。② **CDR** — 添付ファイル内の active content (macros, embedded scripts, OLE objects, JavaScript in PDFs など) を危険と仮定して除去し、利用可能な clean copy を再構築します。添付内部の URL や QR code も書き換え、クリック・スキャン時に RBI を経由するようにします。
  - **なぜ・効果 (Why / Impact)**: シグネチャベース検知やサンドボックスでは構造的に取り逃がす新規・遅延・標的型攻撃のギャップを補完します。クリックとファイル展開という二つの暴露瞬間を contained・recoverable event に転換します。
  - **主要データ**: 本文に定量的なベンチマークの明示はありません (本文情報が不足)。RBI/CDR は Cisco Secure Email Gateway のアドオンライセンスとして提供されます。

- **核心要約** (本文ベース、原文 fetch `selector` 抽出 13,204文字 — retries 0):
  - **何 (What)**: Cisco Talos IR の **AI Tiger Team** が raw notes から long-form technical report を生成する際に LLM が示す inconsistency (不正確性・不自然な結論・文体の混在) の root cause 分析と、prompt engineering ベースの制御方法論を共有。**Tabletop Exercise (TTX) report** 作成を case study として採用しました。
  - **どのように (How)**: 2 種類の inconsistency を特定 — ① **structural** (フォーマット・構造の一貫性不足) → template + 明確な delimiter instruction の組み合わせで predictable・repeatable な結果を確保。② **context drift and pollution** (context window 限界、複数の unrelated task が混在することによる cross-contamination) → レポートごとに新規 session/project で実行することが必須。3 種類の prompt を開発 — "Discussion Organizer"、"Recommendation Polisher"、"Executive Summarizer"。
  - **なぜ・効果 (Why / Impact)**: 標準化された executive summary・recommendation section が要求される専門レポートにおいて LLM 出力の品質を制御。session 分離原則によって cross-contamination を遮断します。
  - **主要データ**: 4 番目の prompt (レポート全体の grammar・spelling 校正) は misspelling 識別には有効だったものの、grammar 問題については false positive (幻覚されたエラー) と false negative (見落としたエラー) が発生し、同一モデル・同一 prompt・同一 draft でも結果が一貫せず **成功率 50% 未満** と評価されました。今後モデル改善に応じて再試験予定です。

- **影響範囲**: LLM の基本概念 (tokens, context window, temperature, top-k/top-p sampling) を学習したい一般・実務読者。CVE・リリース/EOL 通知ではなく、教育コンテンツです。
- **核心要約** (本文ベース、原文 fetch `selector` 抽出 20,964文字 — retries 0):
  - **何 (What)**: Cisco AI ブログの LLM 基礎シリーズ第1回。tokens, subword tokenization, Byte-Pair Encoding (BPE), context window, temperature, sampling などの中核概念を非専門家でも理解できるように整理しています。
  - **どのように (How)**: ① **Tokenization** — BPE 方式、30k〜100k vocabulary、頻出ペアを段階的にマージ。スラング・専門用語・多言語にも対応可能。API コストが token 数に比例 — 英語と他言語の tokenization の差がコストに直結。② **Context window** — モデルが追跡可能な会話履歴の範囲。大きいほど multi-step 指示・大規模 codebase 処理が可能ですが、メモリ・計算量が急増し、200k token 処理は 4k 比でコストが激増。長い prompt の中盤に対する attention が弱まる傾向あり。③ **Temperature** — 0.0 (決定論的) から 1.0 (学習分布通りのサンプリング)、1.0 超で無作為性が増幅。一般的な利用は 0.3〜0.9 範囲。④ **Top-k / Top-p sampling** — temperature より精緻にランダム性を制御する手段。
  - **なぜ・効果 (Why / Impact)**: AI ワークロードを運用・導入するインフラエンジニアや一般ユーザーが LLM のコスト・一貫性・創造性のトレードオフを理解する手助けとなる series intro です。
  - **主要データ**: 推奨 temperature 範囲 — code generation は低い値 (精密性)、creative writing は高い値 (多様性)、カスタマーサポートチャットボットは 0.3〜0.5 (一貫性)。代表的 vocabulary サイズ 30k〜100k。context window 事例 — 200k token 処理は 4k 比でコスト・計算量が dramatic に増加。
