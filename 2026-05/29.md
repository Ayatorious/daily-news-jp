### [CNCF] The Kubernetes integration tax: Prometheus, Cilium and production reality

- **発表日**: 2026-05-28 (木 11:00 UTC / 20:00 JST)
- **カテゴリ**: 機能 (Feature / Platform Engineering)
- **影響範囲**: マルチクラウド (AWS、GCP、Azure、ベアメタル、Hetzner) 環境で 20〜30 件の CNCF プロジェクトスタック (Prometheus、ArgoCD、Cilium、cert-manager、Velero、Sealed Secrets、Kyverno など) を統合運用するプラットフォーム / SRE チーム
- **核心要約** (本文ベース):
  - **何 (What)**: 250 以上の CNCF プロジェクトの中で、本番スタックが頻繁に遭遇する「integration tax(統合コスト)」問題の事例共有。個々のプロジェクトはドキュメント通り正常動作するものの、プロジェクト間の結合点 (gap) で障害が発生し、プラットフォームチームの時間の 80% がインストール・チューニングではなくプロジェクト間の配線に消費されるという診断です。
  - **どのように (How)**: (1) **事例 — cert-manager vs Ingress Controller** — cert-manager の HTTP-01 ACME challenge は平文 HTTP でトークン配信を行いますが、Ingress Controller がグローバル HTTP→HTTPS 強制リダイレクトを適用するとすべての ACME 検証が破綻します。(2) **事例 — Cilium ServiceMonitor 欠落** — Hubble UI では DNS・TCP・HTTP latency が正常表示されますが、Cilium agent/operator Pod に ServiceMonitor が配線されていないと Grafana パネルは空白になります。(3) **Cluster API (CAPI) による 4 クラウド統一** — `eksctl` / `gcloud container clusters create` / `az aks create` の代わりに `Cluster`、`MachineDeployment`、`MachinePool` といった Kubernetes リソース + クラウド provider 変換モデルを使用します。Day-2 アップグレードは `MachineDeployment` の 1 行変更、`MachineHealthCheck` による不良ノード自動排除、DR は management cluster の再生成 + Velero バックアップ復元 + CAPI reconcile で行います。(4) **two-repo GitOps パターン** — Platform repo(100+ Helm chart に Cilium NetworkPolicy・Prometheus ServiceMonitor・cert-manager annotation を事前結合) + Config repo(クラスタごとに変動する値のみ: ドメイン・ノード数・GCP プロジェクト・AWS アカウントロール)。ArgoCD が両方を監視します。(5) **Jsonnet ベースの監視生成** — kube-prometheus スタックを per-cluster vars ファイルから生成し、Velero backup age・CloudNativePG replication lag・kubelet 証明書失効などのアラート mixin を含みます。(6) **NetworkPolicy のチャート内蔵** — 20+ Helm chart に Cilium NetworkPolicy テンプレートを含め、チャート自体が egress 要件を宣言します。
  - **なぜ・効果 (Why / Impact)**: 統合問題はどの単一プロジェクトの issue tracker にも存在せず「gap」に潜むため、デバッグコストが大きくなります。Platform/Config 分離により 1 回の PR が全クラスタへ伝播し、クラスタ別チケット・属人的記憶への依存を解消できます。
  - **主要データ**: CNCF landscape 約 250 プロジェクト / 本番スタック 20〜30 件 / プラットフォームチーム時間の 80% が統合に費やされる / Platform repo 内 100+ Helm chart / 4 クラウド統合検証 (AWS、GCP、Azure、Hetzner + ベアメタル)
- **原文リンク**: https://www.cncf.io/blog/2026/05/28/the-kubernetes-integration-tax-prometheus-cilium-and-production-reality/

### [Cisco Blogs] Unlock the power of scale-across with Cisco converged silicon, systems, and optics

- **発表日**: 2026-05-28 (木 15:00 UTC / 2026-05-29 00:00 JST)
- **カテゴリ**: 機能 (Feature / AI Network Architecture)
- **影響範囲**: 100MW 級 (60,000〜70,000 GPU 以上) のフロンティア AI 学習インフラを複数サイトに分散しようとするハイパースケーラ・サービスプロバイダ・AI インフラ運用者。Cisco Silicon One P200、Cisco 8223、N9000 システム、NCS 1014 metro open line system の検討対象
- **核心要約** (本文ベース):
  - **何 (What)**: Cisco が「scale-across」(DCI: Data Center Interconnect の上に AI 学習 fabric を載せる新しいネットワーク層) ソリューションを発表しました。Silicon One P200 ルーティング + Cisco 8223/N9000 システム + coherent optics を silicon・systems・optics の共同設計観点で統合する内容です。
  - **どのように (How)**: (1) **電力の限界** — 単一 GPU 700W、GPU ラック 80〜150kW、フロンティアモデル学習クラスタ 10〜15MW(小都市の電力需要に相当)、最先端モデルは単一サイトで 100MW(60K〜70K GPU)に接近。単一サイトの電力で賄えず、サイト分散が必要になります。(2) **ネットワーク階層比較** — Scale-up(ラック内、100〜200Gbps/lane の銅、≤3m、DCI 比 504x の帯域幅) / Scale-out(データセンタ内、Ethernet・InfiniBand、約 56x DCI) / Scale-across(データセンタ間 10〜100km、約 7x DCI) / 従来 DCI(エンタープライズ traffic)。(3) **距離の限界** — 数メートル超過時は銅では信号品質を維持できず、pluggable optics または co-packaged optics が必要になります。(4) **輻輳制御** — 100km リンクでは光速の制約により約 100MB のデータが in-flight 状態となり、flow control が応答する前に最新スイッチのバッファのほぼ半分を単一ポート・優先度が占有してしまうため、reactive 輻輳制御では限界に達します。したがって **deep-buffered router**(スイッチではなく)が必須となります。AI ワークロードは予測可能なため proactive 輻輳制御は可能ですが、リンク障害時には deep buffer による吸収が必要です。(5) **光増幅サイト** — DC 間距離・トラフィック増加は fiber plant の光増幅容量とその電力消費を伴うため、silicon・optics 両面での電力最適化が必要です。(6) **Cisco 統合ポートフォリオ** — Silicon One P200(Cisco 8223 / N9000 システム)、coherent optics(C-band・L-band wavelength 活用)、NCS 1014 metro open line system(integrated coherent probe、dynamic gain equalization、OTDR、spectral power monitoring)
  - **なぜ・効果 (Why / Impact)**: AI 時代の本質は「より多くの GPU → より大きな知能」ですが、電力が hard wall として作用しています。単一サイトの電力不足を解決するには、データセンタを 100km 以上分散しながらも同期した学習を維持する fabric が必要です。既存 DCI の 1,000〜2,000 ポートでは処理できないため、silicon-optics の共同設計が first-order engineering problem となっています。
  - **主要データ**: 単一 GPU 700W / GPU ラック 80〜150kW / フロンティアクラスタ 10〜15MW / 次世代学習サイト 100MW (60K〜70K GPU) / 距離 100m〜2km(銅の限界以降)、10〜100km(scale-across)、100km(coherent optics の限界領域) / 100km リンクの in-flight データ 約 100MB / 帯域幅比率: scale-up 504x DCI / scale-out 56x DCI / scale-across 7x DCI
- **原文リンク**: https://blogs.cisco.com/sp/unlock-the-power-of-scale-across-with-cisco-converged-silicon-systems-and-optics
