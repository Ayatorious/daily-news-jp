### [CNCF] How to get engineering time back from Kubernetes upgrades

- **発表日**: 2026-05-11 (月 20:00 JST)
- **カテゴリ**: その他 (Other) — CNCF Blog (Fairwinds 寄稿)
- **影響範囲**: Kubernetes (特に EKS) を自社運用している組織、シニアエンジニアの工数配分に関する意思決定
- **核心要約**:
  - **何 (What)**: Fairwinds が CNCF ブログに寄稿した「Kubernetes アップグレード・保守負荷」分析記事です。Kubernetes を社内運用するか、マネージド/外部 SRE に委ねるかを判断するためのフレームを提示しています
  - **どのように (How)**: 中規模 EKS 環境において、3 リージョンを跨ぐマイナーバージョン1回のアップグレードがエンジニアリング工数で 4〜6 週間を消費し、ロードマップ機能 2〜3 件を後ろ倒しにするという運用知見を提示。Komodor の 2025 Enterprise Kubernetes Report と Black Duck の 2026 OSS Security and Risk Analysis を根拠データとして引用し、Fairwinds 自社の Kubernetes SRE 運用事例にも言及しています
  - **なぜ・効果 (Why / Impact)**: シニアエンジニアの時間を Kubernetes ライフサイクル雑務 (バージョン bump、API 廃止対応、アドオン互換性確認) から外し、デプロイ頻度の改善・インシデント削減・新規収益創出に再配分することを提案。「Kubernetes 自体が製品の一部であるか、10% の効率改善が数百万ドル規模になる組織」でない限り、マネージド委託を検討すべきと提言
  - **主要データ (記事内の引用)**: Kubernetes インシデント対応に1チーム当たり年間 34 workdays / 本番障害の 80% が直近のシステム変更に起因 / ワークロードの 65% が要求 CPU・メモリの半分も使用していない / 商用コードベースの 87% に脆弱性が1つ以上存在し、78% に高リスク脆弱性、44% に critical 脆弱性を含む
- **原文リンク**: https://www.cncf.io/blog/2026/05/11/how-to-get-engineering-time-back-from-kubernetes-upgrades/

### [Cisco Blogs] Improving Labeling Consistency with Detailed Constitutional Definitions and AI-Driven Evaluation

- **発表日**: 2026-05-12 (火 02:19 JST)
- **カテゴリ**: その他 (Other) — Artificial Intelligence (AI)
- **影響範囲**: Cisco AI Defense 利用者、AI ガードレール/コンテンツ分類システムの設計者
- **核心要約**:
  - **何 (What)**: Cisco の新しい安全分類手法「Single-Source Safety Definitions」研究の発表。Cisco AI Defense の安全分類タクソノミ (Safety Taxonomy) 全体をこのモデルへ移行中です
  - **どのように (How)**: 各脅威テクニック (harassment、hate speech、jailbreak など) に対して、必須要素、意思決定フローチャート、隣接テクニックとの境界ルール、ワークド事例、エッジケースを蓄積した 300 行超の「憲法 (Constitution)」仕様書を作成。ランタイム分類時に LLM が呼び出しごとに仕様書全体を再読込みします。Intent (攻撃意図の有無) と Content (実際に有害物が会話に現れたか) を分離した dual-axis 評価により、マルチターン攻撃も追跡します
  - **なぜ・効果 (Why / Impact)**: HarmBench 評価で、人間アノテーター間の不一致が 1,000 件あたり最大 66 件だったのに対し、LLM (GPT-5.4 / Claude Opus 4.6 / Gemini 3.1) を用いた場合は 3 件未満に減少 (最大 57 倍の一貫性改善)。同じ仕様書を読んだ人間 3 名の全会一致率より、LLM 3 種の全会一致率の方が高いという結果。顧客側には、「なぜブロックされたか」を特定ルール・境界単位で追跡可能というメリットがあります
- **原文リンク**: https://blogs.cisco.com/ai/improving-labeling-consistency-with-detailed-constitutional-definitions-and-ai-driven-evaluation

- **影響範囲**: Google ADK ベースの AI エージェントを構築・デプロイするチーム、Gemini Enterprise Agent Platform の Agent Runtime 利用者
- **核心要約**:
  - **何 (What)**: Cisco AI Defense と Google Agent Development Kit (ADK) のランタイム保護統合の発表です。ローカル開発環境と Gemini Enterprise Agent Platform 上の Agent Runtime (ホスティング環境) の双方で同一の保護が適用されます
  - **どのように (How)**: Python 2 行で統合可能 — `from aidefense_google_adk import defend` を実行後、`agent = defend(agent, mode="enforce")` を呼ぶだけです。ADK ライフサイクルフックに直接組み込まれるため、別途コントロールプレーンを構築する必要がありません。Monitor と Enforce の 2 モードを提供し、ブロック時には「blocked and why」decision trace により遮断ポリシーと根拠を出力します。保護済みエージェントはそのまま `agent_engines.AdkApp` でラップして Agent Runtime にデプロイ可能です
  - **なぜ・効果 (Why / Impact)**: エージェントがツール呼び出し・多段階アクションを実行する際に発生する新しい脅威モデル — untrusted prompt content がツール呼び出しを操作したり、ツール出力がモデルへ流入することで機微データが漏洩するシナリオ — をランタイムで遮断します。セキュリティを独立ワークフローとして分離しないため、ローカル開発からホスティング配備への移行時にセキュリティ構成を再設定する必要がありません
- **原文リンク**: https://blogs.cisco.com/ai/protecting-agents-with-cisco-ai-defense-and-google-agent-development-kit
